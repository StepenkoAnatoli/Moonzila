# Moonzila architecture and current decisions

The full product architecture is defined in [reviewed decisions](specification/decisions.md) and the [implementation roadmap](superpowers/plans/2026-09-24-moonaliza.md). This document records current context recovery and offline Research Kit boundaries, not a replacement roadmap.

Electron main owns credentials, provider transport, native dialogs and the process broker. The utility-process engine owns durable SQLite state, project policy, operation approval, journaling and the agent loop. The renderer accesses only the validated preload bridge; its preflight guidance never grants tool or network authority. Errors cross the bridge only as `ErrorCodeSchema` codes (`src/shared/errors.ts`, public messages in `src/main/bridge.ts`); any other code surfaces as `INTERNAL_ERROR`. Tool policy refuses research tools with the contract code `RESEARCH_NOT_ALLOWED`. A refused profile endpoint is the public `INVALID_ENDPOINT`. A hard-linked file met by undo or recovery is the public `HARDLINK_REVIEW_REQUIRED`.

Context assembly is a pure engine operation before every model step. It reserves output capacity, evicts complete historical turns and compacts saved tool outputs into bounded references while retaining current call/result relationships. Originals remain in SQLite; retrieval is bound to the current session and passes live policy and cancellation checks. The UTF-8 estimate is a heuristic. Validated provider usage is a separate optional observation, never an invented exact preflight count. See [context recovery](specification/context-recovery.md) and its [primary evidence](../research/BRIEF.md).

Privacy changes require an explicit project-policy update. The engine's `project.policy.update` (`src/engine/application.ts`) refuses `RUN_ACTIVE` before cancelling anything when the update leaves `inference` unchanged and a non-terminal run of a mode other than `research` is in the project (research switch, `docs/specification/research-review-ui.md` section 4); an `inference` change still stops every run. Profile edits bind to their revision; moving a credential-bearing profile to another endpoint or provider requires a new credential or explicit removal. Context recovery prepares a draft and never automatically repeats model calls, commands or edits. The context-recovery phase required no schema migration; folder-free chat below introduces schema v2 without new dependencies.

Provider streaming and later Research Kit integration must preserve these process boundaries. Research documents and imported artifacts are untrusted reference data, never instructions or permission grants. Genuine managed-model qualification, production trust inputs and signed delivery remain separate requirements.

The offline Research Kit stage adds opt-in guarded execution to the existing process broker. Before launching a child, the native helper opens read-only file guards and ancestor directory guards, rejects reparse points and hardlinked leaves, and waits for the owner to verify bytes and admit execution. Guards last until owned process cleanup. Failed or cancelled admission launches no child, admission has a deadline, and callers may stop the owned tree on output overflow. Ordinary command execution retains its existing behavior.

The [offline consumer](specification/research-kit-offline.md) uses independent strict boundary contracts, a reviewed inventory of 100 external runtime files and actual pinned producer/validator fixtures. It captures archive bytes once, checks bounded archive metadata and runs the pinned CLI with minimal environment and fixed arguments. Validity and research readiness stay separate from application permission. Successful imports retain content-addressed ZIPs outside project instruction discovery; each read verifies bytes against a process-local receipt bound to job/project revision and the complete dispatch identity. Restart requires fresh validation. Stage 2 since added the durable job lifecycle and the renderer surface, described below; renderer requests still never carry paths.

[Folder-free chat](specification/folder-free-chat.md) reuses the engine and conversation store with nullable session/run project identities. A general chat has a revisioned local/cloud policy and zero tool declarations. Main and engine intersect conversation and project policy and bind both revisions to each run. Every project tool entry rejects null scope. Stop, revocation and changed conversation policy invalidate active work.

Schema v2 preserves historical project sessions, runs, messages, FTS, journals and approvals through a transactional create/copy/drop/rename migration. A direct run-to-session FK and matching-scope triggers close the nullable composite-FK gap. Conversation scope is immutable: attaching or switching branches into a new session with only reviewed user text. Source policy restrictions survive branching. Navigation clears drafts; no tool output, approval or provider continuation is copied. Context recovery uses the same privacy-preserving branch with an unsent draft. Creating a session as part of Send never clears a draft until run admission succeeds. Native main-process dialogs are the only route to selecting/creating a workspace, followed by explicit trust. See the [design and migration sources](superpowers/specs/2026-10-01-folder-free-chat-design.md) and [implementation plan](superpowers/plans/2026-10-01-folder-free-chat.md).

Schema v3 makes research jobs run-less durable records: a constrained `research` projection plus an append-only `research_events` journal keyed by revision, with SQL triggers that refuse an unjournaled or stale change, identity rewrites, a second dispatch and `approved`. The engine (`src/engine/research.ts`) owns job state and admission; main drives collector facts through the `research.context/transition/recover` controls. Job notices use a separate `research` engine message, leaving `EventSchema` to runs. v2 research rows are kept verbatim in `research_legacy`. Earlier builds refuse a v3 database; migration is not a downgrade path. Schema v4 (Task 5, `migrateResearchReview`) rebuilds `research` and `research_events` in sqlite.org's documented order (create new tables, copy with explicit columns, drop, rename, recreate every index and trigger, then assert the object list and row counts before `user_version`), and refuses a v3 row in `reviewing` or `approved` with `MIGRATION_RESEARCH_STATE`. It adds the `packaging` status, the `engine` actor, nullable review columns (`review_session_id`, `review_run_id`, `review_digest`, `reviewed_package_sha256`, `reviewed_validator_revision`, `reviewed_bound_revision`) with checks per status, and replaces `research_readiness_reserved` with `research_readiness_digest`: `approved` only from `packaging`, with the frozen digest unchanged, a reviewed package unlike the collected one journaled on `collecting → collected`, and main's `KIT_APPROVED` journal row. `research_reviewed_immutable` freezes an approved row. The review edges live in `research-state.ts`; the store writes the review columns per edge, clearing them when a new review starts, and refuses a review start or retry with `RUN_ACTIVE` while another job holds the project's research slot. A `reviewing` or `packaging` job reaches `not_ready` or `approved` only while its review run holds no live engine work (terminal, absent or `awaiting_review`), so the engine records a run's terminal event before the job's edge. `recoverInterrupted` keeps an `awaiting_review` run that a `reviewing` or `packaging` job names. The engine answers `research.review.context` (the review columns and the completed review writes since the latest `fresh` edge) and `research.recover` fills `freeze`, `packaging` and `reviewDiscard`; `reviewDiscard` never names a job in the owned list, whose workspace main's child may still use.

Collection is owned by main. `src/main/collector.ts` (`CollectorSupervisor`) drives each job from a re-read `research.context` through the pure planner `src/main/collector-plan.ts`, and only an `applied` reply lets it launch. A dispatcher that has started is never stopped, re-launched or re-dispatched; any outcome that could hide a remote run fails the job as `REMOTE_STATE_UNKNOWN`. A learned run id is spooled to `runs/<id>.json` before it is committed, so a lost commit is replayed at the next start. Each launch gets a 30-second vault grant: the token is decrypted only into the child's environment block and the grant is revoked once the launch is handed over. The token never reaches the engine, the database, notices or logs. `ResearchKit.prepareCollector` (`src/adapters/research-kit/adapter.ts`) shares `guardedRun` with the validator. The staged runtime and node are read-locked and rehashed, then the supervisor's admission check runs, and only then may the child start. A failed rehash is `INSTALLATION_INVALID`. Each launch has its own folder under `storage/collect`, and `close()` waits for running children. `src/main/index.ts` wires it in. At start it opens `<userData>/research-kit/collector.json`, builds the kit only from a valid `installation.json` and sweeps it. The collector reference is kept through the vault reconcile, and the supervisor is attached. Engine notices and `research.start/cancel` replies go to `observe`, and every engine child's `ready` goes to `engineReady`. `project.revokeTrust/policy.update` hold the project until the engine applies the change. `project.policy.update` and `run.start` are routed through `src/main/policy-route.ts` (`createPolicyRoute`, engine requests and controls, active runs, vault and supervisors injected): both take one per-project FIFO lock (`run.start` learns its project from the control `session.project`; a missing session or a folder-free chat is forwarded unlocked), and under it, before any signal is aborted, vault context revoked or supervisor held, every update is answered in the engine's own precedence (BRK-1, Phase 4 invariant 3): first replay (the control `request.lookup` with `canonicalHash(params)`; an accepted request is forwarded untouched and the engine answers its stored result, an id reused with another input is `REQUEST_CONFLICT`), then revision (the control `policy.guard`, read once; a stale `expectedRevision` is `REQUEST_CONFLICT`), then `RUN_ACTIVE` for one that leaves `inference` unchanged (a no-op update included) while a non-research run is live; only then does it abort, revoke, hold, forward and release as before. Quit closes the supervisor, then the kit, then the engine. A downloaded package goes to the verified import, `src/main/research-import.ts` (`packageImporter`). It reads the GitHub run once, with the token from a 30-second grant in the request's `Authorization` header only, and no redirect followed. The run must be the one the job dispatched. Its commit and attempt, never the package's, go into the binding with the job's `collecting` revision and admitted policy revision. `ResearchKit.validate` then checks the package and retains its bytes. The supervisor commits the answer through `planStep`. `collecting → collected` requires the verification (digest, validator identity, bound revisions, the run's identity, run id and client ref, download digest unverified), journaled in that step's detail without a schema change. The engine refuses one that does not name the job's own revision, policy revision, run, client ref, repository and short ref. A package from another run fails `PACKAGE_IDENTITY_MISMATCH`, and a run that is not the dispatched one fails `RUN_IDENTITY_MISMATCH`. Anything not the package's fault parks the job as `import` until the next start; `validate` reports an unclassified failure outside the package's own content as `INSTALLATION_INVALID`, not `ARTIFACT_INVALID`. A collecting job's watch deadline is anchored on `dispatchedAt`, else on `createdAt`, so a damaged row is still watched and never past retention. A watch refused with `CREDENTIAL_DENIED` parks for credentials at once only when the saved token reference is gone; with the token still saved it is retried like any other refusal. The start input budget lives once, as `RESEARCH_INPUT_BUDGET` in `src/shared/params.ts`. The whole pre-start step (locks, rehash, admission) is bounded by `admissionMs` through `OwnedOptions.admissionTimeoutMs` in `spawnOwned`. A job held after a commit error stays in `ownedIds()` (and `busy()`) until the next app start, so an engine-only recovery never fails it. A watch counts its not-started refusals in a row, reset by any started watch or a park. The engine re-checks admission when it accepts a package (`collecting → collected`), as it does for the dispatch, inside the same transaction. Retained packages are written under `storage/work` and replaced by rename into the content-addressed store (not documented as crash-atomic on Windows); a torn file there is replaced, and a bad store entry defers as `INSTALLATION_INVALID`. Task 5's frozen review contracts live in `src/engine/review-contract.ts` (workspace, digest, reviewed package, failures, tool messages, review controls); `research.review.start` is main-owned, and so is Phase 4's reader `research.document.read {researchId, document}` (`src/shared/params.ts`): a fixed document name, never a path, and at most 262,144 UTF-8 bytes of redacted text with `source` and `verified` (never verified for the workspace); its outcomes have their own codes, `DOCUMENT_*` (`docs/specification/research-review-ui.md` section 3). Phase 5's `research.purge {researchId}` is main-owned and returns `{removed, keptShared, keptBusy}`, refusing with `PURGE_NOT_ALLOWED` outside approved, failed and cancelled; main reads every job's retained digests through the internal engine control `research.retained` (`src/engine/control.ts`) inside the adapter's storage lock (`docs/specification/research-purge.md`). A review run that ends without a research-ready package fails with the one public code `REVIEW_NOT_READY` (decision D1); the job's `failure` keeps the exact reason. `research.review.context` also returns the verification journaled on `collecting → collected`, which is main's only source for the job's binding when it starts or packages a review (never the package's own manifest). The spec's "Phase 3 as built" section lists where the review build differs from or adds to the design. Each review change it lists carries `status` (`completed` or `unknown`), so main can accept an unrecorded write that did reach the disk when it checks a `continued` workspace, and begin then reconciles it. Admission compares the job's research level and trust revision, not the whole policy revision, so an inference-only policy edit keeps research running. The planner's `FINISHED` set (statuses the collector only releases, including v4's `reviewing` and `packaging`) is the one the supervisor uses; the engine's `research.recover` control passes main's `reviewFolders` through. A job that names a review run ends (`not_ready`, `approved`, or `cancelled` after a cancel) only once that run holds no live engine work; the readiness trigger compares the collected digest lowercased; `reviewDiscard` returns only plain folder names main does not own. SQL fixtures check out with LF on every platform (`.gitattributes`). Internal engine controls `policy.guard {projectId}` (stored policy revision and inference, and whether a non-research run is unfinished) and `session.project {sessionId}` (`src/engine/control.ts`) are the route's reads besides `request.lookup` (P4-10: `session.read` is capped at 10000 runs and returns history). `src/engine/control-dispatch.ts` answers each from one SQL read (`Store.policyGuard`, an `EXISTS` over the project's sessions and runs, finished meaning `completed`, `failed`, `cancelled` or `interrupted`; `Store.getSession`), with no run list or messages; null for a missing project or session.

Review supervisor (Task 5, B3). `src/main/review-workspace.ts` is file I/O only: it materialises the verified bytes' `project/` entries into `storage/review/<id>/staging-<uuid>/project` (archive limits, `validateRelativePath`, create's exclusions, each hash against a strict `files[]` projection, at most 1,900 files) and replaces `project/` by rename; it inventories the tree (any link, junction, hard link or other entry fails), folds completed review writes over the base (`foldExpected`, which no `unknown` write satisfies), folds the trees a kept workspace may be in (`foldAccepted`: an `unknown` write, a crash between its rename and its record, allows its before or its after hash), and computes the review digest. `ResearchKit.prepareReview` runs `preflight.mjs --json`, `brief.mjs` and `artifact.mjs create` through `guardedRun` with `validatorEnvironment(temp-<uuid>)`, fixed bounds and `stopOnOutputLimit`; `create` takes one `--name=value` element per value from the binding, plus the collected manifest's run URL, HTML URL and API version when plainly shaped (Q8). `ResearchKit.verifyRetained` re-validates a retained ZIP under a binding (a missing or changed file is `STALE_VERIFICATION`; its error is decided by the hash of validate's single capture of the file: bytes that do not hash to the digest name, or a real non-PASS verdict on intact bytes, are stale; intact bytes with no verdict (timeout, cut-off or unreadable output, storage limit), or intact bytes main then fails to read, are the internal `VALIDATOR_UNAVAILABLE`, which review start, packaging and the reader map like `INSTALLATION_INVALID` to `RESEARCH_KIT_UNAVAILABLE`); it and `validate` take the caller's abort signal and an optional `admit` check run in the guarded start after the artifact's rehash, `discardReview` removes only plain job folder names under the storage lock, and `sweep` keeps every `review/<id>/project` and removes per-attempt folders; both first require `storage/review` to be a real folder whose realpath is storage's own (else `INSTALLATION_INVALID`), and a job entry that is a link loses only the link. `containedFolder` (review-workspace) is main's side of the engine's `containedReviewWorkspace`: every component from the filesystem root to `review/<id>/project` a real folder, no link or junction, and its realpath the derived one; the supervisor checks it before each step that creates, reads, packages or writes there and again inside each kit child's guarded start (`PATH_OUTSIDE_PROJECT` for start, `REVIEW_TOOL_FAILED` for a kit tool, `not_ready` / `REVIEW_WORKSPACE_CHANGED`, cause `WORKSPACE_NOT_CONTAINED`, for the freeze and packaging). `src/main/review.ts` (`ReviewSupervisor`) owns main's half of the research review. `research.review.start` is answered in main, serialized per job: it refuses `RUN_ACTIVE` only while a command or kit tool of a run in the job's own project executes in main (`projectBusy`; `index.ts` keeps each executing task's project, and a task whose project it does not know counts for every project), reads `research.review.context` (status `collected` or `not_ready`, admission null, the journaled verification), re-validates the retained collected ZIP with the binding built from that verification (`ResearchKit.verifyRetained`), prepares the workspace (`continued` only when a `not_ready` job's tree is one `foldAccepted` allows, so begin can reconcile each `unknown` write against it; else rebuilt `fresh`), sends `research.review.begin` with one request id kept across engine restarts (a begin whose reply was lost replays; after a retried begin, a job left `reviewing` under a run the new engine interrupted is owned, and the driver records `not_ready` / `REVIEW_INTERRUPTED`), and rebuilds `fresh` once if the engine answers `REVIEW_WORKSPACE_CHANGED`; `src/main/index.ts` then installs the run's capability as for `run.start`. The workspace lives at `<userData>/research-kit/storage/review/<id>/project`, the path the engine resolves for the review run. The kit tools reach main as the port message `research.tool`, which `src/main/engine.ts` routes to `EngineHooks.reviewTool` and answers exactly once per request id, with `research.tool.result` or a `ReviewToolErrorSchema` code (anything else, including a result outside the contract, is `REVIEW_TOOL_FAILED`). Preflight's verdict counts only as the whole JSON object with its matching exit, bounded to 200 findings and redacted; the brief is drafted in `scratch-<uuid>/project` and returned as content for an approved write. A kit child's read locks cover what it reads and never what it writes (the helper's locks share only reading): the brief run leaves `research/BRIEF.md` unlocked, which `brief.mjs` replaces by rename. On the run's `awaiting_review` (or recovery's `freeze` list) the supervisor freezes: the tree must equal the fold, and preflight must not report `hygiene/brief-stale` (Q10 b), then `reviewing → packaging {reviewDigest}`. Packaging re-checks the stored digest, runs `create` whose `beforeStart` rehashes the tree and re-reads the job under the read locks, deletes the output on every non-zero exit, retries once on timeout, helper failure or truncation, validates the produced bytes with the packaging revision's binding (a validation without a receipt is `REVIEW_PACKAGE_INVALID` only for the package's own faults; an invalid installation is `RESEARCH_KIT_UNAVAILABLE` and any other fault of this machine `REVIEW_PACKAGING_FAILED`), requires the new manifest's `project/` entries to equal the frozen inventory, and records `approved` only for a research-ready receipt. The freeze and packaging each run under one abort signal shared by all their kit children (the collected package's re-validation, preflight, `create`, the reviewed package's validation), and every one of those children re-reads the job inside its guarded start: the same status, revision and run, a null admission, no hold on the project, not stopped, not quitting; otherwise it never starts and the driver re-reads. A changed admission ends the freeze as packaging (`not_ready` with the admission code), and a hold makes either step wait. A notice that the job left the step's state (cancel, a Stop), a hold and quit abort that signal; main commits `cancelling → cancelled` once no live run remains, and owns a review job's `cancelling` notice for that (a run interrupted under it has no end that would). The collector's `research.recover` call is wrapped in `index.ts` to carry the review supervisor's owned jobs and the `review/` folder names, and the reply's `freeze`, `packaging` and `reviewDiscard` go to the supervisor, which deletes only the folders the engine named.

Research document reader (Phase 4, B11). `src/main/research-document.ts` (`readResearchDocument`) answers `research.document.read` in main (`src/main/index.ts` routes it): the job's `research.review.context` status picks the source. `approved` re-validates the reviewed package under its `boundRevision` with the journaled verification (`reviewBinding`) and extracts only from the buffer `verifyRetained` returned (missing or not verifying: `{text:'', verified:false}`); `collected` does the same for the collected package (`DOCUMENT_UNVERIFIED`); `reviewing`, `packaging` and `not_ready` read `review/<id>/project/research/<file>` with every folder from the filesystem root down to the job a real directory (so a linked parent of the data folder refuses every read: P4-23, its own task in the plan), `containedFolder` (checked again after the read), each component below lstat-checked, an `O_NOFOLLOW | O_NONBLOCK` open (a planted FIFO is refused at once, never waited on) and an fstat matching the lstat's device and inode with one link (else `DOCUMENT_UNSAFE`), at most 4 MiB, and fall back to the collected package only when the job folder or one of its parents is absent (a job folder without `project/`, or a document missing from it or from a verified package, is `DOCUMENT_NOT_AVAILABLE`; any other I/O error is `DOCUMENT_UNSAFE`). Only `STALE_VERIFICATION` from `verifyRetained` reads as missing or not verifying; every other error it throws (`INSTALLATION_INVALID`, `VALIDATOR_UNAVAILABLE`, anything else; `CANCELLED` cannot occur, since the reader passes no signal) and a machine with no kit are `RESEARCH_KIT_UNAVAILABLE`, never Unverified (P4-25). The whole text is decoded, redacted by the vault, then cut to 262,144 UTF-8 bytes at a character boundary; no receipt cache, and refusals carry only their code.

At each completed project step or phase, verify the work, push a branch and open a pull request as a draft. The agent merges it only under the merge checks in AGENTS.md (user decision, 2026-10-04): every S1 and S2 fixed and re-reviewed, the Linux gate matching the baseline, Windows CI green on the exact head, and the PR mergeable with no thread waiting.

The September 30 reconciliation preserves upstream NDJSON/SSE transport, reused-index Ollama tool calls and native no-truncation flags. Accumulators retain validated optional terminal usage for the existing completion/event contract. Malformed usage does not invalidate an otherwise valid answer. Provider refusal inspection is limited to 64 KiB and its text never crosses into the engine. Incremental renderer output is deferred until the reviewed stream masker is implemented. The [Research Kit integration review](specification/research-kit-integration-review.md) is a future-stage design; it adds no runtime dependency or permission bypass.


Local repository access correction (0.8): directory tools accept only the explicit root aliases `.`, `./` and `.\` in addition to the existing empty root. Other path validation, trust, protected files and link checks are unchanged. URL-shaped inputs are rejected before filesystem inspection, without network access. Missing local paths, invalid paths, exclusions and unsupported URLs produce distinct public failures shared by the tool result and durable UI event; raw OS errors and absolute paths remain private. File/Git tool guidance makes the local workspace boundary explicit. The separate [public GitHub reader](specification/github-url-reading.md) implements URL reads through main-owned unauthenticated GET requests. Engine exposes read_github only for repositories in saved user text; main independently checks scope and live run/privacy/epoch before and after reads. Results bind to a run-pinned commit and source URL. General chat gains this remote read capability without any local tools. Cloning and GitHub credential storage are not implemented.

Research panel (plan Task 6, collection part): `src/renderer/ResearchPanel.tsx` opens per project from the details pane and talks only through `research.list/start/cancel` and `research.collector.read/save`, plus the preload's `onResearch` notices, which it filters by project and merges by revision so a late list reply never overwrites a newer notice. The start form groups the fields that become readable on the collector repository and names that repository; `acknowledgedPublic` comes only from an unticked checkbox, is held for the collector repository it was given for, and editing any public field or saving a different collector repository unticks it. The collector token input is uncontrolled: the token never enters React state or a DOM attribute, is cleared after a successful save, and the panel shows only `tokenConfigured`. `src/renderer/research-text.ts` holds one actionable message per job failure in the [collection spec](specification/research-collection.md), a test keeps the two in step, and research text is rendered as bounded plain text with direction controls removed. There is no authorize or approve control; the only review controls are Start review, Open review and Cancel review. A parked watch is not visible to the renderer (the job stays `collecting`), so the collecting state explains the possible waits instead. The import failures `RUN_IDENTITY_MISMATCH` and `PACKAGE_IDENTITY_MISMATCH` have their own messages. A collecting job's hint also says that a corpus waiting for verification resumes at the next start. The panel's active and cancellable statuses (now including `packaging`) are tested against the engine's `ACTIVE_RESEARCH` and its user cancel edges. Review flow (Task 5 Phase 4, B4): Start review with a model picker (cloud profiles disabled under local-only inference) only for `collected` and `not_ready` in a trusted project with research on; Open review (App closes the modal, re-lists conversations, applying the list only while the same project is open, and selects `reviewSessionId`; while the workbench is busy, loading or has an active run, the panel shows Open review disabled with the reason, as the conversation list refuses a switch) and Cancel review for `reviewing`; Cancel review for `packaging`. An `approved` job is never "Ready" from its status: `ApprovedCheck` reads the brief through `research.document.read` and shows Ready (with the reviewed digest's first 12 characters) only on `verified: true`, Unverified on `verified: false`, Cannot check (with Check again) on a rejected call, and discards replies whose job id, revision or reviewed digest changed (`ApprovedCheck` is exported so a test can change the digest alone, which the panel's revision merge never does). `DocumentReader` shows brief and evidence as plain text in a `<pre>` through `displayText`, with source and verification above it. `research-text.ts` adds one entry per engine `REVIEW_FAILURES` code (a test imports the engine list) and `REVIEW_PHASE_FAILURES`, review wording for the admission codes and `RESEARCH_KIT_UNAVAILABLE` that `failureText` uses for a `not_ready` job. Research switch (B8): in a trusted project, `ResearchSwitch` replaces the research-off dead end with Allow research and, when research is on, offers Turn research off; each opens an inline confirmation (`SWITCH_TEXT` in `research-text.ts`) and only its confirm button calls `project.policy.update`, with `inference` exactly as stored and `research` `public-technical` or `off` (never `private-connected`). The preload passes only the public message, so a refusal equal to the bridge's RUN_ACTIVE text (`RUN_ACTIVE_MESSAGE`, kept equal to `src/main/bridge.ts` by a test) reads "Finish or stop the running task first." and is not retried. The panel uses the reply's project until the workbench passes a newer policy revision, and reports it through the optional `onProjectChange`. Delete stored corpus (Task 5 Phase 5, B7b; [research-purge spec](specification/research-purge.md) decision 8): `PurgeControl` is offered for `approved`, `failed` and `cancelled` jobs (`PURGEABLE_RESEARCH`), on the current job and on earlier jobs in the history; it opens an inline confirmation (`PURGE_TEXT`: the brief and evidence can no longer be read, and the record stays; only the current approved job adds that it reads Unverified unless another research job keeps its package) whose confirm button alone calls `research.purge {researchId}`. The reply is parsed with `ResearchPurgeResultSchema` and shown by `purgeResultText` (removed, then keptShared and keptBusy only when they apply); a reply outside the schema is not reported as a deletion, and a refusal shows the public message once, beside the control that was used, in its own state that automatic errors do not replace, until Dismiss or the next purge action. Each settled purge bumps a per-job count in the `ApprovedCheck` and `DocumentReader` keys, so the approved check re-runs and an open document is dropped.

Renderer error ownership (0.8.1): navigation and explicit actions clear prior errors synchronously. The session-loading effect must not clear errors, because a newly created session can finish rendering after run admission has already refused a request. The refusal and retained draft remain visible; this changes no engine admission or recovery authority.

Desktop verification waits for durable terminal run status before checking the rendered GitHub answer. The fixture includes a valid six-second response to prevent reinstating a five-second end-to-end assumption. This test-only correction preserves production request deadlines and requires completed status, exact source identity and restart persistence.

The product is named Moonzila since 2026-10-03 ([decision 12](specification/decisions.md)). The rename changed user-facing names and current documents only; the identifiers that bind an installed app to its data (app ID, `app.setName`, session partitions, IPC channel names, the native helper file name, model-store and receipt identities, the activation signature domain) keep their original spelling. Packaged code loading (Task 5, B5): `electron-builder.yml` `electronFuses` turns off `runAsNode`, `enableNodeOptionsEnvironmentVariable` and `enableNodeCliInspectArguments`, and turns on `onlyLoadAppFromAsar` and `enableEmbeddedAsarIntegrityValidation`, so a packaged build ignores `ELECTRON_RUN_AS_NODE`, `NODE_OPTIONS`, `NODE_EXTRA_CA_CERTS` and `--inspect`, and loads only its validated `app.asar` ([Electron fuses](research/2026-10-03-electron-fuses/research/BRIEF.md)). Main may therefore never use `child_process.fork` with `process.execPath`; the engine starts through `utilityProcess.fork`. `grantFileProtocolExtraPrivileges` stays at Electron's default because the renderer loads from `file://`. `scripts/check-fuses.mjs` reads the fuse wire of the packaged exe through `@electron/fuses` (installed with electron-builder) and exits 1 unless those five match; the Windows workflow runs it after the packaged build, which happens only on `workflow_dispatch`. Because Playwright's launcher needs `--inspect`, the packaged e2e runs on a test-only package (`npm run package:win-e2e`, `release-e2e/`, built right after `package:win` from the same `dist/`, native helper and config) whose five code-loading fuses `check-fuses.mjs --test-package` requires to match the shipped set except inspect, before use ([decision 13](specification/decisions.md); [Playwright and fused Electron](research/2026-10-04-playwright-fused-electron/research/BRIEF.md)).

Review run (Task 5, B2): `src/engine/research-review.ts` is the engine half of the research review. `rootFor(run)` (`createRootResolver`) is the one place a run's files resolve: the project root for every mode but `research`, and `<userData>/research-kit/storage/review/<researchId>/project` (`reviewWorkspacePath`) for a review run, whose job is the one whose review session the run is in. On every resolution `containedReviewWorkspace` requires the workspace root and each folder between it and the data folder to be a real directory, not a link or junction, and realpath(root) to equal the derived path under realpath(data). Otherwise it refuses `PATH_OUTSIDE_PROJECT`, so a link swapped in after a proposal is caught by the journal's re-check before its rename. `Operations.allowedPath`, `FileJournal` (`authority`, `propose`, `apply`, `observeRecovery`, and `undoAuthority`, which now takes the operation's run instead of a fixed Build root) and `FileReader` all ask it. For a review run the protected data folder exempts exactly that workspace, and `assertToolPolicy` allows `write` in mode `research` only when the root is a review workspace. A review run writes only `research/MAP.md`, `EVIDENCE.md`, `BRIEF.md` and `DISCOVERY.md`, checked before an operation is prepared, and only while it is its job's live review run. Review operations keep the run's project, policy and trust revisions, are left out of `changes.list`, `recovery.list` and `requiresReview`, and are never undone. `research.review.context` lists the job's `completed` and `unknown` review writes since its latest `fresh` edge, each with its status, in creation order (an unknown one may or may not be on disk). Control `research.review.begin` (`beginReview`) reconciles a `continued` workspace's unknown review writes (`applied` completes, `not-applied` fails, `conflict` refuses `REVIEW_WORKSPACE_CHANGED`), and a `fresh` begin closes every earlier still-unknown review write in its acceptance (failed, recorded `superseded`), so none can poison a later continued begin; then in one acceptance it checks status, admission, profile, conversation policy and an idle project, reuses or creates the job's review session, creates a fresh `research` run (`assertFreshReviewRun` refuses a reused or terminal one) with Moonzila's fixed instruction, records the edge (`REVIEW_STARTED`, `REVIEW_RETRY`, `REVIEW_RESTARTED`) and appends `run.started`, `message.created` and `research.status`. The run is offered the read tools, `read_tool_result`, `write_file`, `edit_file`, `research_preflight` and `research_draft_brief`, never commands, Git or GitHub. Kit tools cross to main as the `research.tool` port message (`ReviewToolPort`, which waits for main's terminal reply even after Stop); a verdict reaches the agent bounded and labelled untrusted, and a drafted brief becomes an ordinary exact-approval write of `research/BRIEF.md`. `endReviewRun` ends a review run and records its job outcome in one transaction, the run's terminal event first: a final answer gives `awaiting_review`; a failure gives `run.failed` `REVIEW_NOT_READY` and `not_ready` with `REVIEW_RUN_FAILED`, `REVIEW_BUDGET_EXCEEDED` (the message names the step or time limit) or `REVIEW_CONTEXT_LIMIT`; a Stop gives `not_ready` / `REVIEW_STOPPED`, also from `packaging` for an answered run through `run.cancel`'s own branch; a `cancelling` job is committed `cancelled` / `REVIEW_CANCELLED`; a shutdown only interrupts the run, for recovery, and at the next start `recoverInterrupted` fails a `research_preflight` (or any read) operation the crash left `started`, since a read leaves no unknown outcome. `research.cancel` aborts a live review run in the same request and cancels an answered one at once. `ResearchJobs` appends `research.status` to the review run on every step of its job, and main's steps that leave the review end an answered run (`run.completed`, `run.failed` `REVIEW_NOT_READY`, `run.cancelled`). `session.delete` refuses a review session whose job is `reviewing`, `packaging` or `not_ready`. The engine's control switch lives in `src/engine/control-dispatch.ts` (`createControl`), which `src/engine/index.ts` delegates to. Approval card (Phase 4, B4b): `src/renderer/ChangesPanel.tsx` takes the run's `runMode` beside `runId` and labels a write card in a `research` run "Research workspace · <path>" instead of "Review edit · <path>"; the mode is bound to the card when it loads, so a stale card keeps its label until the reload replaces it; buttons, text and `approval.decide` are unchanged. `src/renderer/App.tsx` passes `runMode={activeRun?.mode}`, the same run whose id it passes. App also passes the research panel `onProjectChange`, which re-reads the projects after the research switch so the details pane and the policy revision App sends next are current.
